## 1b. 块 0 详解：SAK `08` 与 `88` 分别是谁给的　【实测 + 规范 + 推断】

这张卡存在一个**两个来源不一致**的现象，读卡器和部分分析工具会因此产生不同判断。

### 块 0（厂商块）的 16 字节布局

| 字节 | 字段 | 本卡值 | 说明 |
|---|---|---|---|
| 0–3 | UID | `00 D0 25 F6` | 唯一卡号 |
| 4 | BCC | `03` | UID 四字节异或：`00^D0^25^F6 = 03`（✅ 计算正确） |
| 5 | **SAK 副本** | **`88`** | 卡内存储的“卡片类型”数据 |
| 6–7 | ATQA 副本（小端） | `04 00`（= 0x0004） | 与芯片应答一致 ✅ |
| 8–15 | 厂商数据 | `C8 12 00 20 00 00 00 24` | 非 NXP 原厂段 |

### 两个 SAK 的来源不同

| 时刻 | 谁在说 | 值 | 可否修改 |
|---|---|---|---|
| 选卡阶段（ISO14443-3 SELECT `93 70…`） | **芯片硬件/固件** | `08` | ❌ 改不了 |
| 认证通过后读块 0 第 5 字节 | **卡内存储的数据** | `88` | ✅ 可写（若权限允许） |

也就是说：**读卡器在选卡时听到的是 `08`，读到块 0 时看到的是 `88`。**

### SAK 常见值对照

| SAK | 含义 |
|---|---|
| `00` | MIFARE Ultralight |
| `08` | MIFARE Classic 1K |
| `18` | MIFARE Classic 4K |
| `20` | ISO14443-4（DESFire / CPU 卡） |
| `28` | SmartMX 模拟 Classic 1K |
| `88` | `0x80 \| 0x08`，即“ISO14443-4 + Classic 1K”双模 |

### 为什么会是 `88`

1. 原厂 NXP MF1ICS50 的块 0 第 5 字节应为 `08`，与芯片应答一致。
2. 本卡是 `88`，且 `88 = 0x80 | 0x08`。按 ISO14443-3，`0x80` 位表示“支持 ISO/IEC 14443-4（APDU）”——而纯 Classic 卡并不支持 APDU。
3. 这说明块 0 是厂家刷入的**模板数据**（兼容芯片厂商常见做法），模板抄自另一类卡，因此与芯片真实应答不符。
4. 结合厂商字节 `C8**0020******24` 非 NXP 段，可判定为**兼容/克隆芯片**（FM11RF08 类）。

### 读卡器的三种反应

| 读卡器行为 | 结果 |
|---|---|
| 只看 SELECT 应答的 SAK（`08`） | 认为标准 M1 卡，正常处理 |
| 读块 0 但只取 UID | 正常处理 |
| 校验块 0 的 SAK / 厂商字节与 SELECT 是否一致 | 发现不一致 → 可能拒绝 |
| 校验厂商字节是否属于合法段 | `C812…` 非 NXP 段 → 可能拒绝 |

### 与“手机模拟卡刷不了”的关系

手机虚拟卡的块 0 为 `XXXX XXXX 6A 08 0400 D200000100000000`：

| 字段 | 实体卡 | 手机卡 | |
|---|---|---|---|
| UID | `A1B2C3D4` | 钱包分配（如 `A618F420`） | ❌ 不同 |
| BCC | `03` | 由钱包 UID 计算 | ❌ 不同 |
| SAK | `88` | `08` | ❌ 不同 |
| ATQA | `0400` | `0400` | ✅ 相同 |
| 厂商字节 | `C8**0020******24` | `D200000100000000` | ❌ 不同 |

数据部分（块 1–63）已做到 bit-perfect，但块 0 四项有差异，且**块 0 被钱包锁定无法写入**。刷水失败说明水控机校验了块 0 的至少一个字段（UID 或厂商字节）。

### 区分“校验 UID”还是“校验厂商字节”的实验

用 CUID 卡写入：**UID 与实体卡相同、厂商字节不同**，然后刷水：

- 能刷 → 系统只认 UID
- 不能刷 → 系统校验厂商字节（此时只有“厂商字节也一致”的 CUID 卡才可能通过）

### 校验算法（已验证）

**末字节 = 前 15 字节逐字节异或**

```
消费前：XOR(前15字节) = 5D，实际末字节 = 5D  ✅
消费后：XOR(前15字节) = 3C，实际末字节 = 3C  ✅
```

复现代码：

```python
def checksum(block15):
    c = 0
    for v in block15[:15]:
        c ^= v
    return c

def make_block(balance_cents, count, flags=0x00):
    b = bytearray(16)
    b[0] = balance_cents & 0xFF
    b[1] = (balance_cents >> 8) & 0xFF
    b[2] = 0x00
    b[3] = flags
    b[4:12] = bytes.fromhex('15D00701A2020400')
    b[12] = count
    b[13:15] = bytes([0x01, 0x02])
    b[15] = checksum(b)
    return bytes(b)
```

## 5. 滚动码 / 防克隆结论　【实测 + 推断】

| 机制 | 是否存在 | 依据 |
|---|---|---|
| 卡内加密滚动码（MAC/挑战响应） | ❌ **没有** | 变化只有明文余额+明文计数器+1字节XOR |
| 明文计数器 | ✅ **有** | byte12 每次刷卡 +1 |
| 双副本同步 | ✅ 有 | 扇区02/03 块0 内容完全相同，刷卡时同步写 |
| 密钥级防克隆 | ❌ 弱 | 全部密钥已破；扇区03–06 甚至把 KeyA 明文存在数据块里 |
| 后台/联网校验 | ⚠️ **未知** | 无法从卡内判断，需行为测试 |

**结论：卡本身没有滚动验证，只有「余额递减 + 次数递增 + XOR 校验」的弱保护。**

真正的风险不在卡上，而在系统侧：如果后台记录了每张卡的余额/次数，克隆卡与原卡交替使用会因数值不同步而被发现。

## 6. 手机虚拟卡复刻实验（三次）　【实测】

### 6.1 第一次：钱包「模拟门卡」读实体卡 —— **只复制到 UID**

用手机钱包的"模拟门卡"功能直接读实体卡，得到的虚拟卡如下：

| 位置 | 实体卡 | 手机虚拟卡 | |
|---|---|---|---|
| UID（块0 字节0–3） | `A1B2C3D4` | `A1B2C3D4` | ✅ **一致** |
| BCC（字节4） | `03` | `00` | ❌ 全零 |
| SAK（字节5） | `88` | `00` | ❌ 全零 |
| ATQA（字节6–7） | `0400` | `0000` | ❌ 全零 |
| 厂商字节（字节8–15） | `C8**0020******24` | `0000000000000000` | ❌ 全零 |
| 扇区 0–8 数据块 | 有真实数据 | **全 `00`** | ❌ |
| 全部尾块密钥 | 各扇区不同 | **全 `FFFFFFFFFFFF`** | ❌ |

块 0 实际内容：

```
实体卡: A1B2C3D4 03 88 0400 C8**0020******24
手机  : A1B2C3D4 00 00 0000 0000000000000000
```

整卡比对：**358 字节 / 30 个块 不同**。

由于尾块密钥全是出厂 `FFFFFFFFFFFF`，这张手机卡只能用 FFFF 读通；用实体卡的密钥去读会在中间某个块认证失败。

**结论**：官方"模拟门卡"对加密卡的行为是 **只写入 UID（4 字节），其余全部留空**。这就是"能复制卡号但复制不了内容"的直接证据。

新空白卡 UID `522F6158`（厂商字节 `D200000100000000`），重新写入：

```
需要写入 64 个块 |...........................x        ← x = 块0 写失败
写入结果：63 / 64
回读块0：522F6158 44 08 0400 D200000100000000        ← 未改变
```

两次不同 UID 的手机卡（`A618F420`、`522F6158`）**块 0 均写入失败**，可确认这是虚拟卡的固定行为，不是操作问题。

### 6.4 结果与推断

| 步骤 | 结果 |
|---|---|
| 钱包模拟原卡 | 只拿到 UID，其余全空 |
| 外部写扇区 1–63 | ✅ 成功、bit-perfect、持久化 |
| 外部写块 0（改 UID） | ❌ 被拒 |
| 拿该手机卡刷水控机 | ❌ 失败 |

推断链条：

1. 手机虚拟卡的块 0 由钱包开通时确定，applet 标为只读 → **无法做到 bit-perfect 复刻**
2. 数据部分可以完全一致，说明"能读能写"这一层手机是支持的
3. 刷水失败 → 水控机校验了块 0 中的至少一个字段（UID 或厂商字节）
4. 若要让 UID 一致，只能让钱包"开户时"读一张 UID 正确的 CUID 中介卡；但厂商字节仍无法与实体卡相同（手机卡固定为 `D200000100000000`）

### 6.5 ⚠️ 实验缺陷（重要，影响第 7 节结论）

**6.2 与 6.3 刷水失败的那张卡，UID 并不是原卡的 `A1B2C3D4`。**

| 实验 | 手机卡 UID | 扇区 1–63 | 是否实刷水控 |
|---|---|---|---|
| 6.1 钱包模拟原卡 | **`A1B2C3D4`** ✅ | ❌ 全空 | ❌ 未测试 |
| 6.2 空白卡 + 补写 | `A618F420` ❌ | ✅ bit-perfect | ✅ **失败** |
| 6.3 新空白卡 + 补写 | `522F6158` ❌ | ✅ bit-perfect | ❌ 未测试 |

因此存在**两个变量同时不一致**（UID 与块 0 后 12 字节），而 6.2 的失败**无法单独归因于厂商字节**。

更可能的解释是：水控机联网按 UID 查服务器账户，`A618F420` 在服务器中不存在 → 直接拒识。这与块 0 的厂商字节无关。

**尚未测试的组合（决定性问题）**：

> UID = `A1B2C3D4`（钱包模拟原卡得到）+ 扇区 1–63 bit-perfect + 块 0 后 12 字节仍为手机值

该组合可以一次性区分“系统只校验 UID”与“系统还校验厂商字节/SAK”。


## 7. 系统行为分析与架构推断　【推断为主，基于持卡人观察】

以下为持卡人实测的行为，是判断“克隆卡能否长期使用”的关键证据，重要性不亚于卡内数据。

### 7.1 观察到的现象

| # | 现象 |
|---|---|
| 1 | 实体卡可刷 **水控机 / POS 机 / 门禁** 三类终端 |
| 2 | 充值后**必须到 POS 机刷卡（圈存）**，金额才写入卡内 |
| 3 | **水控机不能同步充值金额**（水控机无法把余额写进卡） |
| 4 | 水控机使用方式是**使用前刷一次、使用后刷一次**；使用结束后，消费记录可在**服务器**上看到 |
| 5 | POS 机消费后，服务器同样可见 |
| 6 | 手机复制卡（UID 已复制、块 0 未完全复制）**能刷门禁**，但**不能刷 POS 机和水控机** |

### 7.2 架构推断

```
              ┌──────────────────────────┐
              │   服务器（账本）          │
              │  账户余额 / 充值 / 流水   │
              └───────┬──────────┬───────┘
                      │ 圈存下发  │ 消费上报
              ┌───────┴───┐  ┌───┴────────┐
              │  POS 机    │  │  水控机     │
              │ 圈存+消费  │  │  只能扣减    │
              └───────┬───┘  └───┬────────┘
                      │          │
                   ┌──┴──────────┴──┐        ┌──────────┐
                   │  卡内离线钱包    │        │  门禁     │
                   │ 扇区2/3 块0 余额 │        │ 只认卡号  │
                   └─────────────────┘        └──────────┘
```

| 现象 | 推断 |
|---|---|
| 充值后需 POS 圈存才写卡 | 卡内余额是**离线钱包**；充值先进服务器账户，由 POS 执行“下装/圈存”写入卡 |
| 水控机不能同步金额 | 水控机只有**扣减权限**（写小额消费），无圈存权限（写大额充值） |
| 水控机前/后各刷一次 + 服务器可见 | 水控机**联网**，采用“开始-结束”两段式：前一次预授权/开阀，后一次结算并上报 |
| POS 消费服务器也能见 | POS **联网**，实时上报 |
| 手机卡能过门禁 | 门禁**只校验卡号（UID）**，不参与余额逻辑 |
| 手机卡过不了 POS/水控 | 这两类终端校验**卡内数据 + 服务器账户状态**，二者缺一不可 |

### 7.3 关键结论：三类终端的安全强度完全不同

| 终端 | 校验内容 | 克隆难度 | 手机模拟能否通过 |
|---|---|---|---|
| **门禁** | 卡号（UID），可能加白名单 | 极低 | ✅ **能**（已实测） |
| **POS 机** | 卡内数据 + 服务器“待圈存/余额”状态 | 高 | ⚠️ **未验证**（只测过 UID 错误的卡） |
| **水控机** | 卡内余额/次数 + 联网结算 | 高 | ⚠️ **未验证**（只测过 UID 错误的卡） |

也就是说：**同一张卡，在不同终端面前的安全等级不一样**。门禁只用了 UID 这一层，所以手机能冒充（有实测支持）；POS 和水控**很可能是**“卡内数据 + 服务器账本”双因子——但这仍是【推断】，因为现有实验未隔离 UID 变量（见 6.5）。

### 7.4 为什么“完美复制卡内数据”仍然不够

即便做到 bit-perfect（UID、厂商字节、余额、次数、校验全一致），仍有三个不可绕过的点：

1. **服务器账户绑定 UID**：POS 圈存与水控结算时，服务器按卡号查账户。克隆卡若 UID 不同 → 查不到账户 → 直接拒绝。
2. **卡内余额与服务器账本会分叉**：原卡与克隆卡各刷一次，服务器只记录一份流水；两张卡的卡内余额必然出现差异，任一张再刷都会与账本对不上。
3. **圈存只能由 POS 写**：克隆卡无法自主充值，用完后只能靠原卡去 POS 圈存再复制一次（每次都要重新 dump + 写卡）。

### 7.5 由此可推出的实用结论

| 目标 | 可行方案 |
|---|---|
| 只刷门禁 | 手机/手环模拟 UID 即可（已实测可行） |
| 刷水控/POS | **待验证**：若系统只按 UID 查账户，则“UID 正确的手机卡 + 补写数据”即可用；若还校验块 0 厂商字节，则只有 CUID 实体卡或底层模拟方案可行 |
| 想两者兼得 | 无解：门禁要卡号、水控要账本，二者必须同一张物理卡 |

### 7.6 建议补做的三个实验

| 实验 | 做法 | 想验证什么 |
|---|---|---|
| A. POS 圈存前后 dump 对比 | 充值前 dump → POS 圈存 → 再 dump | POS 写了哪些块、是否引入新 MAC/密钥参与 |
| B. bit-perfect CUID 卡刷水 | 用 UID+厂商字节完全一致的 CUID 卡 | 水控是否只校验 UID（若是，则克隆卡可短期使用） |
| C. bit-perfect CUID 卡刷 POS | 同上 | POS 是否要求服务器存在“待圈存”状态 |
| **D. UID 正确的手机卡刷水** | 钱包「模拟门卡」读原卡（得到 UID `A1B2C3D4`）→ 外部写扇区 1–63 → 实刷 | **决定性实验**：区分“只校验 UID”与“还校验厂商字节/SAK” |

## 8. 其他数据特征　【实测 + 推断】

1. **扇区 1 和 7 含 ASCII 卡号串**：`<卡号已脱敏>`（扇区1块0偏移1起、扇区7块2），很可能是系统内部卡号/学工号，而非 UID。
2. **扇区 3/4/5/6 的块 2 存放 `KeyA + FF078069 + FFFFFFFFFFFF`** —— 把该扇区密钥明文复制到数据块，属于自定义校验方案常见做法。
3. **日期字段**：`250913`（扇区2块2）、`250925`（扇区8）→ 2025-09-13 / 2025-09-25。
4. **扇区 8 块0** 含 `B80B0000` = 3000（小端），可能是另一类额度/押金。
5. **扇区 9–15 全空**，未使用。

## 11. 克隆实践与 PN532 底层驱动经验　【实测】

本节记录 2026-11-23 的完整克隆实践，包含三种载体的对比和一个可复用的底层驱动实现
（`tools/pn532.py`，按 Elechouse / Adafruit 官方库的帧格式编写）。

### 11.1 三种载体实测对比

| 项 | 实体卡 | CUID 标签 | 手机虚拟卡 |
|---|---|---|---|
| UID | `A1B2C3D4` | `A1B2C3D4` | `A1B2C3D4` |
| 块 0 | `A1B2C3D4 03 **88** 0400 C8**0020******24` | `A1B2C3D4 03 **08** 0400 C8**0020******24` | `A1B2C3D4 03 08 0400 **0000000000000000**` |
| 块 0 厂商码 | `C8**0020******24` | ✅ 相同 | ❌ 全 0 |
| 块 0 可写 | ❌ 出厂只读 | ✅ 可反复写（SAK 被芯片强制改回 08） | ❌ 钱包锁定 |
| 数据块 | 基准 | ✅ 完全一致 | ✅ 完全一致（48/48 验证） |
| 16 扇区密钥 | 基准 | ✅ 一致 | ✅ 一致 |
| 水控机 | ✅ | ✅ **实测可刷并写回** | ✅ 实测可刷并写回 |
| POS 机 | ✅ | 待验证 | 曾失败（数据不一致时） |

**关键结论**：

1. **CUID 实体克隆卡在水控机上完全可用**——被识别、认证通过、次数被机器改写（69→72）。
2. 水控机**不校验块 0 的 SAK**（克隆卡 08、实体卡 88，照样刷）。
3. 手机虚拟卡的块 0 只有厂商码 8 字节缺失，BCC/SAK/ATQA 已正确复制（由钱包从中介卡读取）。

### 11.2 CUID 块 0 的正确写法

`nfc-mfclassic` 的三种写入模式对块 0 的行为不同：

| 模式 | 块 0 | 适用 |
|---|---|---|
| `w`（普通写） | 跳过块 0（63/64） | 数据块 |
| `W`（解锁写） | 走 gen1a 后门（0x40/0x43） | 仅 gen1a 卡 |
| **`c`（CUID 写）** | ✅ **写块 0，gen2 语义** | **gen2/CUID 卡** |

命令：

```
nfc-mfclassic.exe c a u <dump.mfd> <keyfile.mfd> f
```

实测：一条 `c` 命令即可把 UID 改成目标值（`CA9D6380` → `A1B2C3D4`）。
但**该 CUID 芯片会把块 0 的 SAK 强制归一化为 `0x08`**，写入 `0x88` 后回读仍是 `0x08`。

### 11.3 PN532 裸指令驱动的三个坑（已解决）

自己写 PN532 驱动时踩到的坑，均已在 `tools/pn532.py` 修复：

| 现象 | 根本原因 | 修复 |
|---|---|---|
| 认证返回 `7F`（无效帧） | 认证帧**缺少 UID**；MIFARE 认证帧格式为 `60 <blk> <key6> <uid4>` | 按 Elechouse / Adafruit 官方实现，帧尾追加 4 字节 UID |
| 写块判定失败 | 该固件写成功只返回 `D5 41 00`，没有 MIFARE 的 `0x0A` ACK | 判定放宽为 `D5 41 00` |
| 连续认证全部失败 | **认证失败会让卡片进入 HALT 状态**（libnfc 源码注释明确） | 每次认证失败后重新选卡 |

官方实现的依据：

- Elechouse `PN532.cpp`：`mifareclassic_AuthenticateBlock()` 在 key 之后追加 UID，长度 `10 + uidLen`
- Adafruit `PN532.py`：`params = [0x01, key_number, block, key..., uid...]`

### 11.4 弱耦合下的写入策略：按扇区写

整卡写需要连续 64 次交互，手机 NFC 耦合不稳时中途掉线即全部作废（实测 15 轮只成功 2 次部分写入）。

改为**按扇区写入**后一次成功：

```
每扇区：认证 → 写 4 块 → 成功则标记
失败：重新选卡（清 HALT），下轮只重试该扇区
```

实测结果：手机虚拟卡 **16/16 扇区、48/48 数据块** 一次写入完成并通过逐块比对。

### 11.5 三卡同步状态（最终）

| 卡 | 余额 | 次数 | 金额 | 块 0 差异 |
|---|---|---|---|---|
| 实体卡 | 185.97 | 72 | 9.46 | 原卡（SAK=88） |
| CUID | 185.97 | 72 | 9.46 | SAK=08 |
| 手机卡 | 185.97 | 72 | 9.46 | 厂商码 8 字节为 0 |

三张卡的扇区 02/03 块 0 完全一致：`A548000017D00702B2030400480100D3`

**风险**：任何一张刷卡后即再次分叉；三者混用会被后台对账发现。

### 11.6 复现步骤（完整）

```powershell
# 1. 读卡（需要密钥表）
python tools/pn532.py read 0 F3DD1B9B0343 A

# 2. 写整卡（按扇区、自动重试）
python tools/phone_write.py

# 3. 验证
python tools/wait_verify.py 600

# 4. CUID 写块 0（改成目标 UID）
nfc-mfclassic.exe c a u dump.mfd keys.mfd f
```

## 12. 完整实验总结（水控机 vs POS 机验证逻辑）　【实测】

### 12.1 实验时间线（全部真实发生并有数据留档）

| 序 | 事件 | 卡内余额 / 次数 | 结果 |
|---|---|---|---|
| 1 | 实体卡水控消费 1.91 元 | 197.34/66 → 195.43/67 | 扣费精确 |
| 2 | 实体卡食堂 POS 消费 9.46 元 | → 185.97/69 | POS 改动多字段 |
| 3 | 手机卡（直接模拟实体卡）刷食堂 POS | 余额一致、次数 70 vs 实体 68 | ❌ **失败，未写任何字节** |
| 4 | 手机卡（经 CUID 中介）刷水控 ×2 | 195.43/67 → 69 | ✅ 成功并被写回 |
| 5 | 手机卡刷食堂 POS 消费 1.00 元 | 185.97/76 → 184.97/77 | ✅ **成功** |
| 6 | 手机卡刷水控消费 0.05 元 | → 184.92/78 | ✅ 扣费精确 |

### 12.2 两个终端的写入字段对比（最硬的证据）

| 字段（扇区02/03 块0） | 水控机 | POS 机 |
|---|---|---|
| 余额 [0:2] | ✅ 精确扣减（1.91 / 0.05 元都对） | ✅ 扣减 |
| 次数 [12] | ✅ +1 | ✅ +1 |
| **金额字段 [8:10]** | ❌ **完全不动** | ✅ **会改**（9.46→10.46） |
| **偏移 [4:7]** | ❌ **完全不动** | ✅ 会改（`15D0`→`17D0`、`01`→`02`） |
| 校验 [15] | ✅ 重算 | ✅ 重算 |
| 失败时 | 未测 | ❌ **一个字节都不写** |

**结论**：水控机是**纯扣费终端**（只碰余额和次数）；POS 是**交易终端**（写更多字段、失败即拒且不写）。

### 12.3 两次 POS 实验的差异（关键但未完全分离）

| 变量 | 食堂失败 | 刚才成功 |
|---|---|---|
| 卡来源 | 钱包**直接**读实体卡 | 钱包读 **CUID 中介卡** |
| 块0 BCC | `00` ❌（应为 03） | `03` ✅ |
| 块0 SAK / ATQA | `00` / `0000` ❌ | `08` / `0400` ✅ |
| 块0 厂商码 | 全 0 | 全 0（相同） |
| 卡内次数 | 70 | 76 |
| 实体卡次数 | 68（差 2） | 76（差 0） |

⚠️ **两个变量同时变化**，严格来说无法单独归因。但从教程证据看，**块 0 残缺的嫌疑更大**。

### 12.4 中介卡的真正作用（纠正常见误解）

大多数教程说“中介卡是为了拿到卡号”，实测表明**不止于此**：

| 钱包读什么 | 直接读实体卡（加密） | 读 CUID 中介卡（未加密） |
|---|---|---|
| 能读到的块 0 | ❌ 只有 UID | ✅ 整个块 0 |
| 生成的块 0 | `UID + 12 个 0`（BCC 错） | `UID + 03 08 0400 + 8 个 0`（BCC 正确） |
| 能否刷 POS | ❌ | ✅ |

**中介卡的本质作用：让钱包能复制块 0 的合法字段（BCC / SAK / ATQA），而不是只复制 UID。**

### 12.5 关于“钱包显示加密卡”

| 现象 | 实测影响 |
|---|---|
| 钱包提示“加密卡，可能不可用” | **不影响水控机刷卡**（已验证） |
| 提示来自钱包的密钥字典探测失败 | 与卡片实际能力无关 |
| 是否影响 POS | 未证实；POS 失败那次同时也是“直接模拟”的卡 |

所以“显示加密”只是钱包的界面判断，**真正的差异在块 0 的内容**。

### 12.7 仍未解决的问题

1. **POS 失败的确切判据**：块 0 的 BCC 还是次数连续性？需要做“块0 残缺 + 次数一致”的对照实验。
2. **金额字段 [8:10] 的语义**：POS 消费 1.00 元时 +1.00，但更早一次 9.46 元的消费却是 6.74→9.46（不符累加）。需要再刷一次不同金额的 POS。
3. **偏移 [4:7] 的语义**：POS 会改，水控不动，疑似交易流水或累计计数。
4. **服务器账本机制**：看不到后台，只能从卡片行为反推。
